## 2026-09-10 (mobile gesture hardening, on-device probe)
- [Fix] the desktop/mobile split pointed at the gesture code, which only runs on a phone: iOS Safari ignores `user-scalable=no`, so page-level pinch zoom has to be refused in CSS and events for the *whole* document. It was only refused over `#stage`, so a two-finger gesture that started on the fixed header, hint or controls was handed to the system, which zooms the entire page and rasterises the whole wall at that zoom. Now `touch-action: none` covers `html, body`, two-finger `touchstart`/`touchmove` and `gesturestart/change/end` are refused document-wide, and a double tap cannot page-zoom either. (Unverified on iOS; the reasoning is that a phone pinches and a desktop does not, which is exactly where the two diverge.)
- [Feature] `?probe=1` bisects a device by itself: the page reloads into each `?off=` variant, drives a synthetic two-finger pinch and pan (the mobile-only path) and records survival in `sessionStorage`, so a tab that gets killed reloads and the run continues from where it stopped. It ends on a verdict screen listing which configurations survived, which turns "test these URLs by hand" into one page load on the phone.
- Verified: the probe walks all eight variants and ends on its verdict in both Chromium and WebKit with no page errors.

## 2026-09-10 (bisecting the iOS crash against the build that worked)
- Measurement that reset the investigation: the build the user confirmed as fixed (e2d9707) decodes **278 MP** - all 101 photos at full 2048px, about 1.1 GB of RGBA - on a dpr-3 phone profile and does **not** crash, while the current build decodes 19 MP and does. Decode volume and image memory were therefore never the cause, and the tier work (while still a worthwhile data/CPU saving) was aimed at the wrong suspect.
- [Fix] `z-index` on the fixed bottom-chrome was the only compositing-related property this refactor added (a systematic diff of every CSS property and DOM API against e2d9707 shows `will-change`, `translate3d`, `filter` and `backdrop-filter` are all absent from the current build - the last two were present in the build that worked). A fixed element with a `z-index` is exactly the kind of thing that makes WebKit put the page into one composited layer and hand the scaled wall a giant backing store, which is the same class of bug the other agent fixed by removing `will-change`. It was unnecessary (the chrome comes after `#stage` in the DOM, so it paints on top anyway) and is gone, along with the z-index on the diagnostics overlay.
- [Feature] `?classic=1` (URL, no rebuild) switches to the rendering path of the build that worked: always the full-size copy (no tier swaps), frames are plain divs instead of links (no click/focus/drag handlers), and one transform on the wall container instead of the screen-space camera. It exists so a device that misbehaves can be bisected in a single build, or simply used as a fallback; `?debug=1` reports which mode is active.

## 2026-09-10 (screen-space camera)
- [Fix] the device reports pointed at rasterisation rather than decode volume - iOS reloaded at 24-35% zoom (barely past the opening view) and Android janks past ~50%, both of which scale with how much wall is on screen, not with the number of images. The camera now works the way a map does: each frame is positioned in screen space for a "baked" camera (`translate() scale()`, origin 0 0), and `#world` carries only the difference while a gesture runs, so the compositor transforms an already rasterised picture instead of re-laying out and re-rasterising a 6792x7088 wall at the new zoom; when the camera settles (140ms) the frames are re-baked crisp and the container returns to identity. Measured on a dpr-3 phone viewport: composited layer footprint at the fitted view 28.7 -> 12.9 MP, mid-gesture 29.6 MP / 123 layers -> 20.4 MP / 91 layers. Panning mid-gesture is now a pure container translation.
- [Fix] frames were mis-scaled in the first cut of that change: an element scales about its own centre by default, so the frames needed `transform-origin: 0 0` (caught by an invariant check that compares every frame's screen rectangle with the layout maths; it now agrees within 0.5px at 12%, 84% and 340%).
- [Fix] removed a no-op clip: the photo box had `overflow: hidden` and the image its own `border-radius`, but the image and the blurred placeholder are exactly the box, so the clip drew nothing while still costing a mask layer per photo.
- [Feature] `?lite=1` (URL, no rebuild) turns the per-frame effects off - mat shadow, corner radii, blurred placeholders - as a diagnostic A/B to isolate what a device can afford; the `?debug=1` overlay reports the mode and the peak decoded figure.
- Note: a frame-pacing test under 6x CPU throttling showed no difference between the two camera architectures (headless Chromium does not reflect paint cost), so the evidence for this change is the layer footprint plus the device reports, not a synthetic frame-time win.

## 2026-09-10 (focus jump, on-device diagnostics)
- [Fix] the wall flashed/jumped when starting a drag on a photo: pressing a link focuses it, and the focus handler panned the frame into view, so the wall moved before the drag began (and then dragged from the wrong base). Focus only moves the view now when it comes from the keyboard (a recent pointer press, or a non `:focus-visible` focus, is ignored). Verified: zoom is unchanged while holding a press on a photo, the drag pans, and tabbing still pans a frame into view.
- [Feature] opt-in diagnostics for the device-only crash: `?debug=1` on the URL (or `"debug": true` in the config) shows a small overlay with zoom, device pixel ratio, visible frames, loaded images, decoded megapixels, the tier mix, the queue length and the peak decoded figure. The last run's peak is kept in `sessionStorage`, so after a tab that was killed and reloaded (a kill does not fire `pagehide`) the overlay opens with a "last run: reached 340%, 42 images loaded, 470 MP peak decoded" line - a number to act on instead of a guess.
- [Fix] guard against a whole class of build breakage: the page's engine script is generated from a template literal, where a stray backslash escape silently changes the output (a regex literal became a line comment, a newline landed inside a string literal). `scripts/check-build.js` now compiles the built script with `vm.Script`, and the test suite compiles both the normal and the debug page, so a page that cannot initialise can no longer pass the checks - the earlier CSS variable check was added for the same reason.

## 2026-09-10 (drag fix, camera moves, iOS hardening)
- [Fix] the wall could only be dragged in the gaps between photos: the frames became links, and a link (with an image inside) is natively draggable, so grabbing a photo started a native drag instead of panning. Frames are now `draggable=false` with `-webkit-user-drag: none`, a prevented `dragstart`, and `-webkit-touch-callout: none` (which also stops the iOS long-press preview/save sheet from firing while panning). Verified: dragging from the middle of a photo pans the wall (transform changes, nothing opens), the frame anchor is the only hit target (pointer events are off for the frame's contents), and a tap after a drag still frames the photo.
- [Fix] camera moves (click-to-frame, keyboard pans) are now driven by `requestAnimationFrame` instead of a CSS `transform` transition, so the wall is never handed to the compositor as one animated layer to rasterise - the same code path as panning and pinching, and the shape of allocation that mobile Safari fails on. Reduced motion still jumps straight to the target.
- [Fix] more iOS hardening in the same direction: `-webkit-touch-callout: none` (no long-press image sheet during a pan), and the frame's inner elements no longer receive pointer events at all.

## 2026-09-10 (iOS zoom, click to frame)
- [Fix] mobile Safari reloading the tab while zooming. Measured cause: with a 3x device pixel ratio the tier threshold worked out to ~85 CSS px, so as soon as the wall zoomed past the fitted view almost every frame fetched its 2048px copy - a short zoom pulled 42 full-size copies and 118 megapixels of decoded image data (a 3x-phone profile). Now: a third 768px tier covers the common zoom range, tier decisions treat the device as at most 2x, the smallest covering tier is chosen, sources swap only after the view settles (140ms debounce, cancelled by movement), four frames per pass nearest the centre first, and a frame only steps down below 0.7x of its tier edge. The same zoom now decodes 19 megapixels with no full-size copy at all (desktop: 73 -> 30 megapixels).
- [Feature] clicking a photo frames it: the view zooms in or out and pans so the clicked photo sits on screen with a small margin (measured: 69% of the viewport width, 86% of the height, from the fitted view). Cmd/Ctrl/Shift-click, middle-click and Enter on a focused frame still open the full-size file, so the link behaviour and the keyboard/screen-reader path are unchanged.
- [Fix] frame links never received mouse clicks: `setPointerCapture` on the stage retargets the click to the capture element. Pointer capture is now taken only once a drag actually starts, so a plain click reaches the frame while dragging still works off-stage, and there is a stage-level fallback that resolves the frame under the pointer.
- [Fix] restored two details of the pre-refactor rendering path that this round had changed: no `border-radius` on the `<img>` itself (the clipping box keeps it), a zero-height chrome container, and no `backdrop-filter` next to the transformed wall (the chips are opaque enough that it made no visible difference).
